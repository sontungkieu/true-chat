Project Goal

Make RAG retrieval measurable, comparable, and usable in chat

Benchmark first

  • Load BEIR-style datasets.
  • Run the same queries across multiple retrievers.
  • Save per-query and aggregate metrics.

Pluggable retrieval

  • Central strategy registry.
  • Consistent interfaces for sparse, dense, graph, and LLM-assisted search.
  • Aliases make CLI and chat mode share the same behavior.

Chat integration

  • OpenAI-compatible proxy response.
  • Retriever metadata returned with each answer.
  • Groq and optional MiMo model routing.

Benchmark Algorithm

The evaluation loop isolates retrieval quality from generation quality

for retriever in selected_retrievers: retriever.build(documents) for query in benchmark_queries: hits = retriever.search(query, top_k) retrieval_metrics = compare(hits, qrels) if generation_enabled: answer = llm.generate(query, hits) answer_metrics = compare(answer, references) aggregate_metrics() write_jsonl_json_csv()

Measured retrieval metrics

  • hit@k: at least one relevant document appears.
  • mrr@k: rewards earlier first relevant hits.
  • ndcg@k: rank-aware graded relevance.
  • precision@k and recall@k: quality and coverage.
  • retrieval_latency_s: per-query retrieval time.

Strategy registry5 / 16

Sparse Baselines

BM25 remains the core lexical baseline

BM25

  • Tokenizes document title and text.
  • Builds BM25Okapi over tokenized documents.
  • Ranks by BM25 score and deterministic doc index tie-break.

TF-IDF

  • Uses scikit-learn TfidfVectorizer.
  • Scores by sparse dot product against the query vector.
  • Very low query latency.

Keyword Match

  • Counts matched query terms and frequency.
  • Adds phrase bonus for exact query substring.
  • In chat mode, an LLM extracts keyword variants first.
Lexical retrieval6 / 16

Expansion and Fusion

Query expansion improves coverage, but fusion decides the final rank

Deterministic multi-query

  • Starts from the original query.
  • Removes common instruction stopwords.
  • Adds keyword-only and split-query variants.
  • Merges BM25 results with reciprocal-rank fusion.

Reciprocal-rank fusion

score(doc) = sum(1 / (rrf_k + rank))

  • Documents found by several query variants rise in rank.
  • Uses rank rather than raw scores, so heterogeneous retrievers can be merged.
  • The project uses rrf_k = 60.
Fusion is the bridge between lexical BM25, dense vector search, graph expansion, and direct dictionary matching.
RRF and expansion7 / 16

Graph BM25

A lightweight document-term graph expands BM25 candidates

Seed Run BM25 and keep seed documents.
Terms Select graph terms with useful document frequency.
Expand Add query terms and high-IDF terms from top seeds.
Score graph Propagate term evidence to neighboring documents.
Rerank Combine normalized BM25 and graph scores.

Implementation weights

Final score uses 0.65 * lexical + 0.35 * graph.

Why it matters

It tries to recover related documents that share discriminative terms with strong BM25 seeds.

Dense and Hybrid Retrieval

Vector search helps semantic datasets, but lexical signal still matters

Vector

  • Encodes documents with SentenceTransformers.
  • L2-normalizes embeddings.
  • Uses FAISS inner-product search when available.

Hybrid RRF

  • Runs BM25 and vector retrieval.
  • Merges ranked lists with RRF.
  • Best SciFact hit@3 in the reported run.

Vector Rerank

  • Starts from vector candidates.
  • Adds normalized BM25 score.
  • Uses 0.7 * lexical + 0.3 * vector.

Dictionary Graph Pipeline

Domain documents become a validated graph-backed retriever

Build-time pipeline

  • Parse DOCX entries into stable entry ids.
  • Use provider extraction for aliases, concepts, categories, and relations.
  • Validate nodes and edges with Pydantic and ontology constraints.
  • Export JSONL, SQLite, GraphML, HTML visualization, and quality report.

Runtime retrieval

  • Direct accent-insensitive headword, alias, concept, abbreviation, and phrase matching.
  • BM25 lexical search over entries.
  • Graph BM25 expansion.
  • Weighted dictionary merge: direct hits get the strongest boost.
This is the domain-specific part of the project: it preserves rich Vietnamese dictionary formatting while exposing normal RAG retrieval hits.

Operational Design

LLM calls are treated as measurable operations, not hidden magic

Key rotation

Groq keys are loaded as aliases only. The system tracks usage without exposing secret values.

Rate scheduling

Per-key or shared 60-second token/request buckets reduce avoidable rate-limit failures.

Retrieval LLM accounting

LLM-assisted retrievers report calls, latency, token usage, retry count, and errors separately from answer generation.

This makes it possible to compare quality gain against latency and token cost.

Conclusions

Best choices depend on dataset semantics, latency budget, and operational cost

For exact scientific claims

BM25 is a strong baseline. Hybrid RRF and vector-rerank improve top-k quality, but need vector build cost.

For semantic medical retrieval

Dense vector search and hybrid fusion beat pure BM25 on NFCorpus hit@3 and nDCG@3.

For production chat

Expose retriever metadata, track token/latency costs, and choose LLM-assisted query expansion only when it proves value.
